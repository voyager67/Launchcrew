# Growth and launch workflow

1. Identify target audience, painful job, existing alternatives, product proof, current maturity, and the one action you want a launch reader to take.
2. Write one specific value proposition: audience + problem + practical outcome. Avoid grand claims, “10x” promises, and fake urgency unless substantiated.
3. Verify project readiness: clean setup, working quick start, license, known limitations, issue templates, contribution path, screenshots/demos only if real, and a concise changelog.
4. Prepare channel-native drafts rather than pasting the same promo everywhere: technical forum post, short social post, professional update, direct maintainer outreach, and changelog/release note.
5. Explain why this exists, how it works, who benefits, what is genuinely different, and what feedback would be most valuable. Link a working demo or exact quick-start path where possible.
6. Build a small targeted outreach list based on relevance. Personalize each message and respect community rules; never automate mass unsolicited messages, tag unrelated maintainers, or ask people to star in exchange for benefits.
7. Set a feedback loop: track questions, onboarding failures, adoption signals, issue themes, contributor conversion, and what changed because of feedback.
8. Define launch success using observable signals and a time window. Use stars as one signal, not as a proxy for user value.

## Deliverables

- Positioning statement and audience
- README hero/pitch review
- Channel-specific drafts
- Launch-day checklist and follow-up cadence
- Ethical outreach criteria
- Learning metrics and feedback triage

## Guardrails

Never fabricate downloads, users, endorsements, benchmark improvements, or inbound interest. Do not spam. Distinguish a launch goal from a guaranteed outcome; neither attention nor inbound email can be promised.
